<acceptance_criteria>

## AC-1: Persisted analytics
```gherkin
Given the user has a valid local demo session and the database is reachable
When they open supervisory analytics and select a valid reporting period or indicator
Then the page and API return only database-derived values, formula labels, and available history
And synthetic-data and training-threshold disclaimers remain visible
```

## AC-2: Bounded exception search
```gherkin
Given the user is signed in
When they filter exceptions by text, institution, period, severity, or status
Then the API applies validated parameterized filters and bounded pagination in SQL
And the page shows the current result count, severity, and review status
```

## AC-3: Traceable signal detail
```gherkin
Given a synthetic exception exists
When the user opens its linked institution or report
Then the signal shows its observed value, training-only threshold, period, and source report
And it is clearly presented as a review signal rather than an official finding
```

## AC-4: Explicit input and service failures
```gherkin
Given a filter value is invalid, the user is unauthenticated, or PostgreSQL is unavailable
When they request analytics or exceptions
Then invalid input and missing authorization produce explicit errors
And database failures are visible as service errors rather than fabricated empty results
```

</acceptance_criteria>
